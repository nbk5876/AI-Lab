Build Journal #004 left cc-sync confirmed but untested — a channel with nothing real running through it yet. That changed almost immediately: qwen3:8b, running through Open WebUI on Node A, seemed to have no memory within a single conversation. This became the channel's first real multi-round work cycle — CC1 writing the spec and reviewing, CC2 building and investigating.

The Gotcha Worth Catching Early

Before writing anything, CC1 researched qwen3:8b's actual context window. Its model card lists 32,768 tokens natively — but Ollama's runtime default is only 4,096 tokens regardless of what the model supports, unless num_ctx is passed explicitly on every request. Missing that would have silently undercut any memory fix before it started.

Part 1: A Standalone Memory Script

The spec called for a Python script wrapping Ollama's /api/chat endpoint: a JSON history file in Ollama's own message format, real token counts pulled straight from Ollama's own prompt_eval_count/eval_count fields rather than estimated, oldest-first truncation with the system message always pinned in place, and a configurable token budget.

CC2 built it (num_ctx=8192, 6,000-token budget) and tested it with a 4-turn conversation deliberately built to create ambiguity — "favorite programming language" versus, later, "favorite language" meaning a spoken language. The model resolved the ambiguity correctly, with visible reasoning proving it was actually tracking context rather than just matching keywords.

One detour along the way: Node A turned out to have no real Python install, only the Windows Store stub. The official installer failed silently twice before an elevated manual run finally succeeded — worth remembering if this needs doing again on a fresh machine.

The Review Round

CC1's review of the script caught three things: the model's own internal reasoning text was being saved into history and resent every turn, silently eating into the token budget; the truncation path had never actually been exercised by a real test; and the history file's location was needlessly computed instead of being a plain, readable constant. CC2's follow-up fixed all three — including deliberately shrinking the token budget until truncation actually fired, to prove it worked rather than just assuming it would.

Standalone memory script: DONE

Part 2: The Question That Actually Mattered

The standalone script solved an adjacent problem — the real complaint was Open WebUI's own chat interface. Asking "I really like the Russian language" and then, in the same thread, "what is my favorite language?" got back "I don't have access to your personal preferences or data," as if the first message had never been sent.

What Got Ruled Out

CC2's investigation was read-only throughout — no production settings touched. Three theories fell, one at a time: no hidden system prompt is telling the model it has no memory (checked directly; none exists). It isn't a context-length problem (actual usage was nowhere near the 4,096-token default ceiling). And it isn't a message-count cap (no such setting exists in this version of Open WebUI).

The Evidence That Actually Held Up

Ollama reports a prompt_eval_count with every response — how many tokens it just processed. In the repro conversation, that number was identical on both turns, proof the second question's request never actually carried the first turn's history. The same pattern showed up in all fifteen of the most recent chats checked — systemic, not a one-off — and it held up against the standalone script's own token counts from Part 1, which grow normally turn over turn in the same environment. The trail led into the installed Open WebUI's own source code, where a code path exists specifically to handle reasoning-model history correctly — present and accounted for, but not yet confirmed whether it's actually running on every request.

Where It Stands

Open WebUI in-thread memory bug: DIAGNOSED, fix not yet applied

The standalone script from Part 1 works as a stopgap outside Open WebUI's own interface in the meantime. Confirming and fixing the underlying Open WebUI behavior is ongoing.

Update: the diagnosis above didn't hold up under closer inspection — see Build Journal #006 for what a live request capture actually found.

Primary Lesson

Three plausible theories got ruled out one at a time by direct checks, but none of them were what actually proved the bug — an identical number showing up twice in a row is what did. That's the same discipline that turned up the wrong-tailnet mixup back in Build Journal #003: when something looks fine on the surface, find the one piece of evidence that can't lie, rather than trusting the plausible-sounding theory.
