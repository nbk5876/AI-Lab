Part 3 diagnosed the problem: after roughly four hours of idle, Lab PC 2 (ai-lab-b) drops off the Tailscale tailnet, and no amount of remote knocking brings it back — only local physical activity does. powercfg /a revealed why: the Beelink SER9 only supports Modern Standby (S0 Low Power Idle), a client-oriented power model that suspends network availability during deep idle. Part 4 applies the fix and proves it with the same test methodology that caught the failure.

Core distinction

Part 3 = diagnosing why remote access fails after idle.

Part 4 = removing the failure state and proving it stays removed.

The standard of proof is the same protocol that produced Test 14's failure: leave the machine completely untouched for hours, then attempt access from the iPhone. If the fix is real, the exact scenario that failed before must now succeed.

Goal #

Configure Lab PC 2 so it never enters the idle state that takes ai-lab-b off the tailnet — the display may sleep, but the computer must stay reachable — and verify the change with repeatable idle tests.

Step 1 — Capture the Baseline SleepStudy #

Before changing anything, generate the SleepStudy report so the pre-fix idle behavior is documented rather than assumed. From an elevated PowerShell or Command Prompt:

powercfg /sleepstudy

The report is written to:

C:\WINDOWS\system32\sleepstudy-report.html

Copy it somewhere safe before it gets overwritten by later runs. The report should show the Modern Standby sessions from the Test 14 window — when the machine entered low-power idle, how long it stayed there, and which components were active or suspended during the session.

What the baseline proves

Across months of standby sessions, the machine was never once woken by network traffic — only by local input or Windows' own maintenance scheduler. The Test 14 failure wasn't bad luck or a Tailscale bug: at the OS level, an inbound request was never a wake candidate at all.

The maintenance scheduler does briefly wake the machine on its own timetable (it ended the 18-hour session), but those wakes are momentary — the box drops straight back into standby, so the node still reads offline whenever a human actually tests it.

Step 2 — Apply the Power Settings Fix #

The fix has two halves: the system must never sleep, and the display should still turn itself off. Both are one-line powercfg commands (elevated prompt, AC settings — the mini PC is always on wall power):

# Never enter standby while plugged in powercfg /change standby-timeout-ac 0 # Display may still sleep after 10 minutes powercfg /change monitor-timeout-ac 10

Verify the active plan picked up both values:

powercfg /query SCHEME_CURRENT SUB_SLEEP STANDBYIDLE powercfg /query SCHEME_CURRENT SUB_VIDEO VIDEOIDLE

A standby timeout of 0 means "never." This directly removes the state Test 14 caught the machine in: with no standby transition, there is no S0 Low Power Idle session for Tailscale to disappear into.

Test 18 — Reboot Resilience #

The idle fix covers the common case, but a Windows Update reboot at 3 a.m. is the other way a "server" silently becomes unreachable. This test checks what survives a restart with nobody at the keyboard.

First, enable Tailscale's unattended mode so the tailnet connection comes up before anyone logs in: Tailscale tray icon → Settings → Run unattended. Then:

  1. Restart Lab PC 2.
  2. Do not log in. Walk away.
  3. From the iPhone, check whether ai-lab-b comes back green in Tailscale.
  4. Attempt to load http://100.115.162.13:8080.

Expected split result: Tailscale should return (unattended mode runs as a system service), but Open WebUI and Ollama likely will not — the Start AI Lab script is a manual double-click, not a boot task. If so, that's not a failed test; it's the next finding, and the fix (a Task Scheduler at-startup job for the Start AI Lab script) becomes its own documented step.

Escalation Path (If Test 16 Fails) #

If the node still drops off the tailnet with standby disabled, the next suspects in order:

  1. Wi-Fi adapter power management. Device Manager → network adapter → Power Management tab → uncheck "Allow the computer to turn off this device to save power." Also set the power plan's Wireless Adapter Settings → Power Saving Mode → Maximum Performance.
  2. Disable Modern Standby entirely via registry — the known workaround for mini PCs whose firmware misbehaves in S0:
    reg add "HKLM\SYSTEM\CurrentControlSet\Control\Power" /v PlatformAoAcOverride /t REG_DWORD /d 0 # then reboot
    This is reversible (delete the value and reboot) but is a bigger hammer — try it only after the simpler fixes are ruled out, and re-run powercfg /a afterward to confirm the change.
  3. Wired Ethernet. Already on the long-term list from Part 3 — removes Wi-Fi power saving from the equation entirely.

Each escalation step, if used, gets its own test number and its own before/after entry here.

Future Note — Model Keep-Alive #

Observed during the informal 20-minute spot check (July 7): the Open WebUI page loaded immediately, but the standard cat-purring prompt took ~90 seconds to complete while reporting only 14 seconds of thinking. The gap is Ollama's model eviction: by default a model is unloaded from RAM after about 5 minutes without requests, so the first prompt after a quiet stretch pays a cold-start reload from SSD.

This is a latency effect, not a connectivity problem — a separate phenomenon from the standby issue this page fixes. The machine stayed reachable; the model just wasn't warm.

Planned tuning: extend the keep-alive window to two hours by setting an environment variable on Lab PC 2 before Ollama starts:

setx OLLAMA_KEEP_ALIVE "2h" # then restart Ollama (Stop AI Lab / Start AI Lab)

Trade-off: the model stays resident in RAM for the full window. A follow-up mini-test could measure warm vs. cold response time for the same prompt.
