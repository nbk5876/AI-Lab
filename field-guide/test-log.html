How to read this log

Every test has a number, a client device, and a validity ruling. Tests marked Invalid were run from the HP laptop while its Tailscale client was silently stuck in NoState — they measured nothing and are kept only for honesty. The standard test prompt is "Answer in one sentence only: why do cats purr?"; timing comparisons use that prompt unless noted.

Test 24 — Open WebUI's displayed thinking-timer is wrong

Client / targetBrowser on Lab PC 2, then browser on the HP desktop over the network → ai-lab-b:8080, plain query, no RAG
ResultOpen WebUI's on-screen "Thought for Xs" timer showed <1s on every round, 10+ rounds across both machines. Real latency, confirmed two independent ways (stopwatch and Ollama's own total_duration captured via a proxy), agreed within 1–3s every round: 20–49s per round
Root causeConfirmed upstream Open WebUI backend bug — not the frontend, not RAG, not the lab's proxy, network, or infrastructure. A persisted chat record showed the broken displayed value (duration: 0) and Ollama's real timing (total_duration = 21.80 s) side by side in the same message, proving the two timestamps used to compute the display don't bracket the real thinking phase. Mechanism is a working theory, not proven — see Part 5 for where this investigation started
Where the seconds actually goNot hidden or mysterious once measured: qwen3:8b generating at ~10–12 tok/s accounts for the real 20–49s directly. Not RAG, not the network, not a proxy tax
Test 24 Result: Displayed-timer bug confirmed and root-caused — real latency matches Ollama's own reported timing throughout; not a lab infrastructure issue

Test 25 — Quantifying the thinking-off and output-length levers

Client / targetLab PC 2, querying Ollama directly (:11434) — no Open WebUI, no proxy, so Test 24's timer bug can't contaminate the numbers
Design2×2: qwen3:8b thinking on/off × prompt unconstrained/one-sentence-constrained. 10 scored trials per condition, median reported
ResultMedian of 10 trials per condition:
A — think ON, unconstrained: 89.29 s total, 1206 tok, 13.4 tok/s
B — think OFF, unconstrained: 34.80 s total, 476 tok, 13.8 tok/s
C — think ON, constrained: 21.54 s total, 301 tok, 14.1 tok/s
D — think OFF, constrained: 1.69 s total, 19 tok, 15.1 tok/s
FindingTurning thinking off cuts time 61–92% depending on condition — bigger than the ~halving guess that motivated the test. The visible answer stays about the same length either way (~2300 vs ~2110 characters), so the extra tokens with thinking on are essentially all hidden reasoning, not a longer real answer. Token rate held in a tight 12.8–15.1 tok/s band across all four conditions, confirming it's token count driving time, not generation speed. Combined levers (A→D): ~53x faster
ScopeQuantify-only, per the decision on the open questions in the test spec — no persistent thinking-off configuration change made or proposed as a follow-up
Test 25 Result: Both hypotheses confirmed — disabling thinking and constraining output length combine for up to ~53x faster responses, with token throughput steady throughout

Conclusions After Tests 1–13 #

Tests 1–13 established that the AI Lab stack can provide both local and remote inference, while revealing an unresolved intermittent remote-access reliability issue. Open WebUI listens on all interfaces (0.0.0.0:8080), Ollama loads and runs qwen3:8b, and the complete iPhone → Tailscale → Open WebUI → Ollama path completed multiple queries. Successful iPhone tests ran 40–71 seconds against 44 seconds locally — Tailscale is not the bottleneck; most delay is model inference on CPU.

Remote access was temporarily unavailable during Tests 3–5 despite the local stack later being found operational. Tests 1, 2, 7, and 8 are invalid for evaluating Lab PC 2 because the HP laptop's Tailscale client was later found in NoState. The open question — whether remote access survives extended S0 Low Power Idle — became Test 14.

Conclusions After Tests 14–19 #

Test 14's open question is answered. The SleepStudy baseline confirmed the root cause: the Beelink enters Modern Standby a median of 17 seconds after display sleep, and across 77 standby sessions (122.6 hours) it was never once woken by network traffic — remote requests were never wake candidates at the OS level.

The fix — standby-timeout-ac 0 with monitor-timeout-ac 10, applied July 7 — removed the standby transition while letting the display sleep. Remote access then succeeded after 6 h 02 m untouched idle (Test 16) and again after ~6.5 h a second night (Test 17a): the exact scenario that failed in Test 14. MagicDNS name-based access is confirmed from iPhone-on-cellular and from the recovered HP desktop (Tests 19, 17b).

New secondary finding: with Ollama's default 5-minute keep-alive, the first query after a long idle can exceed the request timeout while the model reloads from SSD ("Load failed," Test 17a) — a latency failure, not a connectivity failure; retry succeeds. Measured reload cost ≈ 1–1.5 minutes (121 s cold vs. 44 s warm). Planned mitigation: OLLAMA_KEEP_ALIVE=2h, after Tests 17 and 18 complete.
